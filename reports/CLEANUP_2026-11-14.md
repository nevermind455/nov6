# Cleanup and consolidation, 14 November 2026

Scope: the whole native C++ bot (`src/`, `include/`, `tools/`, `tests/`,
`scripts/`, CMake, CI and docs), starting from `main` at 84a2b15. The aim was
to remove what is not used and keep one implementation of each thing, with
no change to trading behaviour. Nothing here changes order pricing, trigger
thresholds, decisions, position sizing or risk limits. No real order was sent:
every live-mode run used the local fake venue and an offline test key.

How "unused" was decided: the linker listed every function that no program
(bot, tools, tests, benchmark) keeps. That build had inlining off, so a
function used only through inlining still counted as used. Then every struct
member, setting and helper was searched by name across the source. Each
candidate below was then read by hand. Nothing was removed on its name alone.

## A. The clean source package

`sniper-native-cpp-clean-2026-11-14.zip` holds the cleaned bot as source: `src/`,
`include/`, `tests/` (with fixtures), `tools/`, `scripts/`, `third_party/`,
`docs/`, `CMakeLists.txt`, `.env.example`, the CI workflow, `README.md`,
`CHANGELOG.md`, and the written reports in `reports/` (plus
`dependency_packages.json` and `linkage.txt`, which the docs cite). It
leaves out build output: the prebuilt `bin/` programs (the VPS still gets
those from git), the generated logs and evidence files under `reports/`, and
`reports/SHA256SUMS` (it lists the git tree, `bin/` included). Every file in
it is the committed file. It was checked by unpacking it into an empty
folder, building it from scratch with the documented commands and running
the tests there (results in D).

### Dependency removed: simdjson 3.6.4

`src/runtime.cpp` created a `simdjson::dom::parser` and allocated 8 KB for it at
start-up. Nothing ever parsed with it: every JSON parse in the bot goes through
nlohmann JSON. Removed with it: `find_package` and the link in CMake, the
`libsimdjson-dev` package in CI and the README, the step in `scripts/build.sh`
that copied the library into `lib/`, the binaries' `$ORIGIN/lib` search path,
and the entries in `docs/DEPENDENCIES.md` and `reports/dependency_packages.json`.
The bot now needs only system libraries (OpenSSL 3, libstdc++, libc).

### Dead code removed

* **Functions nothing called:** `WebSocket::up_since`, `Dashboard::interactive`,
  `Dec::digits`, `Dec::adjusted`, `Dec::integral`, `Ledger::drawdown_pause`,
  `Sniper::bankroll_value`, the `Side` enum with `side_name` and
  `token(Round, Side)`, and `Ledger::risk_rebase`'s `pause_until` parameter,
  which no caller passed.
* **A dead branch:** `latency_plan`'s "live-sampled" delay branch and the
  `SniperEnv::live_delay()` hook it called. No implementation ever returned a
  value, so the branch never ran.
* **Fields written but never read:** `Plan::decided_ns`, `built_ns`,
  `signed_ns`, `sent_ns` and `lat_parts` (`lat_parts` was a full JSON copy made
  per order); `Sniper::t1_ns_`; `PaperResult::matched_mono`; the paper broker's
  `filled_orders`, `rejected_orders` and `refused_real`; the book's
  `dropped_inactive` (with `note_inactive_drop`) and `rejected_updates`; the
  freshness gate's `trades` and `trade_without_e`; `PaperConfig::latency_ms`
  and `flagged_delay_ms`; `SniperSettings::delay_source` and `delay_days`.
* **The ledger's durable drawdown pause** (`Ledger::dd_pause_until` and
  `drawdown_pause()`). Only a test set it, and nothing read it. The real
  drawdown pause runs in memory (`SNIPER_HYBRID_DRAWDOWN_PAUSE_S`). Older
  builds refuse a ledger whose snapshot or risk rows lack these fields, so the
  ledger still writes `dd_pause_until` and `pause_until`, always 0. A ledger
  written by this build therefore still loads in the previous build (rollback),
  and a test holds both fields.
* `.gitignore`: two Python-only rules.

### Settings that were accepted but did nothing

These were found, not caused, by the cleanup. Behaviour is kept, and each one
now prints a start-up notice instead of being ignored silently:

* `SNIPER_DELAY_SOURCE=live`: sampled live delays were never implemented here.
  Paper delays use the model, exactly as with `model`.
* `PAPER_LATENCY_MS` and `PAPER_FLAGGED_DELAY_SECONDS`: still checked to be
  numbers, but nothing reads them. Paper delays come from `SNIPER_LATENCY_MS`
  or the live-like model.

Proposed, **not applied**: refuse `SNIPER_DELAY_SOURCE=live` at start, as
`SNIPER_FILL_ODDS=live` already is. That would stop a `.env` that sets it from
starting, so it is left for the owner to decide.

### Optimizations (measured below)

* `DurableLog::append` (the synced journal row written before each order is
  sent) serialized the event twice and deep-copied it once. It now serializes
  it once and writes the same bytes. A test compares the two byte for byte,
  with quotes, backslashes, newlines, control characters, UTF-8 (accents,
  emoji), 0.1, 1e300, -0.0 and the integer limits.
* `Ledger::register_intent` moves the event into the journal instead of
  copying it.
* The removed `Plan::lat_parts` saves one JSON copy per decision.

### Left as is, on purpose

* **Signing, the EIP-712 digest and the order's wire body.** Signing is one
  libsecp256k1 call (about 35 us). The digest and the wire bytes are what the
  venue verifies. Changing them is a correctness risk for no measured need.
* **Decision arithmetic.** It is an exact emulation of Python's numerics, so
  decisions match the reference digit for digit.
* **The fdatasync before each send.** It is the crash-safety rule: an order on
  the wire is always on disk first.
* **`src/runtime.cpp` (4,095 lines).** Splitting it would add files without
  removing code, and would risk behaviour.
* **Helpers in the standalone report tools.** `sf` and `pct` in `live_check`
  and `feed_race` differ (percent nearest-rank vs fraction floor), and merging
  them would change those tools' output.
* **`config.cpp`'s `.env` trim** (space, tab, CR, LF) differs from `py::strip`
  (also VT and FF), so it stays separate.
* **`Round::market_id`.** It is stored and never read. Removing it would also
  drop the implicit requirement that every listed market has an `id`, which
  changes what discovery accepts from a malformed reply.
* **`order_digest()`.** Only tests use it: it is the hook for the digest test
  vectors.

Investigation of the one-order difference. The two bots have their own
connections to the venue, so the same messages reach them a few milliseconds
apart. The trigger compares prices by arrival time, and the paper model waits
in real time for the book at the order's modelled arrival. A small shift in
timing can therefore move a signal, or decide an arrival check, either way.
The recorded pair shows this: each bot's input gives identical decisions in
both builds, and the inputs themselves differ. So the difference is in the
input, not the code.

### Production-ready?

The cleanup itself is verified as far as it can be away from the VPS. The bot
makes the same decisions, writes the same ledger bytes, applies the same risk
checks, and shows no sanitizer report. Its ledgers load both ways between
the old and new builds.

Not verified, so not claimed:
* runs against the real Polymarket, Coinbase and Binance (no access from here);
* runs on the VPS;
* runs with real money.

For those, nothing in this cleanup changes the existing go-live path
(`docs/GO_LIVE.md`): pull on the VPS, a paper run, then the live canary. On
this evidence alone the bot is **not** declared production-ready. It is
declared no less ready than the previous build, with the same behaviour.

### Updating the VPS

Stop the bot, `git pull`, start it again. The pull deletes
`lib/libsimdjson.so.19`, which the new `bin/` programs do not need (the old
ones did, so do not mix an old `bin/` with the new tree). The ledger and the
journal carry over as they are.
