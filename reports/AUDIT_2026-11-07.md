# System audit — 7 November 2026

Repository: `nevermind455/nov6`. Audited base:
`f31a7b12214326c84348b3294f8dcfc8f8e0e1e9`. Fix branch:
`audit/full-system-2026-11-07`. This report describes the additional audit after
the earlier three-fix review documented in `REVIEW_TEST_REPORT.md`.

During the audit, remote `main` advanced independently to
`c4c2c9dac79fa00ec628ad213cf1d2df277fe534`. Those changes were incorporated
before final validation and reviewed as part of the final system: the new
native edge-report tool, venue long-decimal parsing, confirmed-miss spend
refunds, inherited-order reconciliation and updated live-preparation settings.
The findings also cover defects in those newly received changes. The owner's
quarter-Kelly/cap choices were retained; first-session preparation was made
consistent with the existing $5 preflight requirement.

The audit found defects affecting HTTP/2 memory safety, recovery and capital
integrity, stale collateral, fill-cap accounting, market identity validation,
paper execution, numeric boundaries, launcher checks and execution reporting.
The accompanying changes fix the demonstrated causes and add regressions.
They preserve the existing strategy parameters, gate order, minimum policies
and risk protections. No real order, funded-wallet test, production deployment
or production-state migration was performed.

This is a source and available-evidence audit, not a certification that an
unbounded system contains no further defects. The repository contains no
verified live executions from which live win rate, real P&L, adverse-selection
cost or production latency can be calculated. Synthetic fills and historical
microbenchmarks are identified separately below.

## Market requirements and order sizing

Official documentation checked during this audit:

* [Resolution](https://docs.polymarket.com/concepts/resolution): the start/PTB
  and final price use 60-second Chainlink TWAP windows. Coinbase triggers and
  synthetic/first-spot observations are not the official settlement oracle.
* [Fees](https://docs.polymarket.com/trading/fees): taker fee follows the
  market's rate/curve; the crypto example is `shares × rate × p × (1-p)`.
  At rate .07 and price .50, ten shares incur .175 quote units before the
  venue's fee rounding, equal to 3.5% of $5 notional. Maker fees are zero in
  the documented schedule; this bot does not implement a maker strategy.
* [Place orders](https://docs.polymarket.com/trading/place-orders): the venue
  defines `min_order_size` per book and tick-dependent amount precision.
  The minimum is market metadata, rather than a universal hardcoded size.
* [Protocol migration](https://docs.polymarket.com/migrate/polymarket-v2/api-integrations):
  choose IDs by market protocol; legacy `clobTokenIds` and newer `positionIds`
  are not interchangeable. Exchange-v3 signing is outside this implementation.
* [Realtime order updates](https://docs.polymarket.com/trading/realtime-order-updates):
  distinguish matched, matched-not-broadcast, mined/retrying and confirmed
  evidence. The additional legacy pending status is accepted; the newer
  unified camelCase envelope is not thereby implemented.
* [RTDS to PolyBolt migration](https://docs.polymarket.com/migrate/rtds-to-polybolt):
  authenticated TWAP channels are distinct from spot feeds. No official
  streaming TWAP connection was added or activated.
* [Geographic restrictions](https://docs.polymarket.com/api-reference/geoblock):
  execution eligibility depends on the venue/account rules. The UK/London
  case can be close-only, with a documented approved-colocation exception;
  possessing a London VPS alone does not establish permission to open orders.

Read-only public Gamma, CLOB market-info and book responses were inspected on
7 November 2026 around 10:36–10:37 UTC. The observed BTC 5-minute market was
explicitly v1, with .01 tick, five-share `min_order_size`, and fee rate .07 /
exponent 1. This is a point-in-time observation, not a permanent hardcoded
promise. Runtime discovery checks the exact five-minute slug, BTC/5m/60-second
TWAP metadata, start/end instants, active/accepting state, distinct UP/DOWN
labels/tokens, condition and rule/book consistency before use.

The unexpected five-share behavior has more than one cause. The observed
venue book publishes a five-share minimum, and the preserved strategy also
uses a legacy five-share floor. Live pre-send checks enforce venue minima,
integer/cent-compatible size, at least $1 marketable notional, cash/reserves
and caps. A price such as .501 can need ten integer shares for whole cents;
at low prices the $1 floor can require more than five shares. A computed Kelly
target below those constraints can be refused or rounded according to the
existing minimum-entry policy. These protections were not removed to produce
more trades. Minimums are loaded from current market metadata and can change.

The code has **no supported maker/resting-order execution path**. Enabled
maker features refuse configuration. Supported live dispatch is a protected
BUY FAK amount order for a share-sized plan; native quote/signing helpers also
cover FOK. FAK unfilled remainder does not rest. Signing fixtures, HTTP replies,
partial fills, empty matches, rejections, private confirmations, cancellations,
unknown writes and reconciliation were reviewed. An HTTP ACK/match is not
treated as proof of a confirmed booked trade. Ambiguous writes keep exposure
and are reconciled, never resent.

The new `sniper-edge-report` is a separate native read-only analysis program.
It calculates settled-sample P&L and round-clustered confidence intervals; it
does not place orders, validate future profitability or create missing trade
evidence. Missing default companion files are allowed, but missing explicitly
requested files refuse. CLI exit 0 means valid analysis (including `NO DATA`),
1 means incomplete/invalid/untraceable evidence or I/O failure, and 2 means
invalid arguments/explicit missing paths. A partial report may be printed
with exit 1 to show what needs repair. Its minimum-round argument must be a
complete positive integer; insufficient calibration cannot certify an edge.

This supports specific readiness/liquidity/price-band explanations; it does

realized loss is $3.23564 and cash is $996.76436. The audited edge report says
`TOO EARLY` for that one-round sample. This verifies accounting arithmetic;
it does not identify an avoidable live loss or establish strategy performance.

The preserved paper arrival model defaults to 14 ms network + 250 ms hold +
25 ms server + 200 ms paper extra = **489 ms**. A paper order waits at most
another 500 ms for the ordered market stream to pass its arrival instant.
Sparse requotes, disconnects or REST-only snapshots can therefore produce
`UNKNOWN_BOOK_STATE`. The reference has the same conservative behavior;
`SNIPER_BOOK_QUIET=1` remains an explicit opt-in. It was not enabled here.

The source also deliberately blocks signals for stale/disconnected feeds,
backlog/freshness checks, warmup, cooldown/in-flight orders, invalid or crossed
books, expired rules, late-round safety, insufficient fair margin, sizing or
cash limits, own exposure, unknown order recovery, and canary/hard-stop budgets.
These are not automatically defects. The active-rule copy bug and malformed
input handling above could cause avoidable blocks; changing the strategy's
price bands, fair margins, delay model or risk limits was outside this audit.

Higher fill frequency is not evidence of better returns. Fees and spread can
consume a small modeled edge; fast taker fills can coincide with adverse
selection, model/oracle mismatch or market movement during delay. The supplied
logs do not contain live execution/markout data to attribute these costs to
particular real losses. No profitability improvement, live fill-rate gain or
directional-accuracy measurement is claimed.

## State migration and recovery constraints

Snapshot v2 adds integrity verification; it is not a Python-ledger migration.
Legacy v1 native snapshots load, their existing checksum/sequence-protected
WAL is still replayed, and subsequent snapshots use v2. Additive fill-slot
fields recover their original session from retained intent events where
available. A crash between positive evidence and slot restoration is repaired
on startup. Legacy stateless refund histories are attributed from retained WAL transitions;
wrong-session or duplicate legacy refunds affecting the current budget refuse
startup for reconciliation. A missing snapshot with nonempty history is deliberately refused
because the original initial bankroll cannot be reconstructed safely.

Before upgrading an existing installation, stop it and back up its complete
state directory, including snapshot, WAL and canary state. **Older binaries
cannot read v2 snapshots.** Rollback requires a compatible binary or a matching
pre-upgrade snapshot/WAL pair, and any subsequent live activity must first be
reconciled. Never replace current live accounting with stale backups, delete
history to get past startup refusal, or edit checksums to conceal corruption.
This audit did not touch production state. The SHA-256 checks detect accidental
corruption; they are not authentication against a party able to rewrite the
state and recompute its checksum.

## Remaining risks and acceptance limits

* No actual live order/fill history exists in the supplied evidence. Real
  acceptance, partial-fill reconciliation, fees, balances and P&L still need
  comparison with the user's account in a separately authorized small canary.
* The 24-hour VPS paper run, real-venue replay captures, complete fault matrix
  and week-long bounded-memory test remain outstanding acceptance work. A
  short local paper test cannot establish these. Global accounting/trade
  history is retained for correctness and can hit configured capacities.
* CTF v1 only; no exchange-v3/protocol-v2 support, deposit-wallet type 3,
  unified realtime schema migration, authenticated PolyBolt TWAP client,
  automatic redemption, maker orders or automatic external-position import.
  Unsupported enabled strategy features continue to refuse.
* A host-local wallet lock cannot coordinate separate servers/other bots.
  Existing external wallet activity is not automatically imported. Shutdown
  prevents new submissions; it does not liquidate holdings. Winning token
  redemption remains a separate account action.
* Cash watermarks are intentionally conservative between samples. Network
  disconnects, unknown outcomes and late evidence can pause trading while
  preserving reservations. This protects exposure and may reduce frequency.
* Unit/loopback tests do not exhaust WAN/proxy chains, resolver faults,
  every callback reentrancy schedule or arbitrary resource-exhaustion input.
  No ThreadSanitizer, exhaustive fuzz campaign or blanket leak-free claim
  beyond the sanitizer test execution is made.
* Strategy profitability is unproven. Model calibration, adverse selection,
  spread/fees, oracle basis and delays require actual execution/markout data.
  No strategy/risk gate was weakened to increase fills.
